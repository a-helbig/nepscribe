How NEPScribe is put together

A map of the whole app: what runs where, where the data comes from, how each tab works, and how a person-year script gets assembled.

Overview Files The data Explore Datasets Transform Data Script generation Shared state Worth knowing Common changes
In one paragraph

NEPScribe is an R package that wraps a single Shiny app (run_app()). It has no database and never touches real survey data. It ships NEPS semantic structure files: the SUF .dta files with every observation removed, leaving only variable names, labels and metadata. Explore Datasets reads that metadata into a searchable table. Transform Data collects the user’s choices and hands them to gen_script(), which assembles an R or Stata script line by line. The user then runs that script on their own copy of the real data.

1 · The big picture

There are four layers. The browser shows the UI. For each browser tab, one R session runs the server logic. That logic calls plain helper functions, and the helpers read files that ship inside the package. Nothing is written back to disk. The only thing that leaves the app is the generated script.

3 · The data the app runs on

Each folder inst/extdata/scN_semantic_files/ holds one starting cohort’s semantic structure files. They look like SUF datasets but have zero rows, so they can ship publicly. A lot of logic reads information straight from the file name:

Metadata lives in Stata “characteristics”

Beyond names and labels, every NEPS variable carries metadata stored in the .dta file as Stata characteristics (called expansion fields by readstata13): NEPS_varlabel_en, NEPS_questiontext_de, NEPS_questiontext_en and so on. read_exp_fields() in utils.R is the single reader for all of it. It opens a file with one column and one row, and returns a long table with the columns variable, type and value. Everything with _de / _en suffixes is how the German/English label switches work.

linkage_keys.csv: which datasets can be merged

This semicolon-separated table lists every dataset with its merge keys. A dataset with an empty Linkage column can’t be merged into a person-year dataset as-is. The Info column (in German) says why. The first rows:

Dataset;Linkage;Info;Sptype
SC6_Basics_S_.dta;"""ID_t""";;
SC6_Biography_S_.dta;;nicht mergebar da schon im personenjahresdatensatz;
SC6_Children_S_.dta;;Nicht mergebar - separat anbieten;
SC6_CohortProfile_S_.dta;"""ID_t"" ""wave""";;

Two helpers read it: create_dataset_names() produces the list for the Additional Variables dropdown, and create_linkage_data() adds the merge keys to each confirmed dataset so the script knows how to join it (ID_t, ID_t wave, or spell keys with splink).

4 · Explore Datasets

A read-only browser for metadata, built as a chain of reactives. Each step waits (req()) for the one before it, so nothing is read until the user has picked something.

The table is a DataTables widget in server-side mode, so paging, sorting and searching are handled by R and the browser only ever holds one page. A leading marker column shows a grey ＋ on variables that can be sent to Transform Data. That feature is covered in the separate note dev/cross-module-wiring.html.

5 · Transform Data

Transform Data doesn’t transform any data itself. It collects choices from three places, and when the user clicks Preview Script or Download Script, it passes all of them to gen_script() in one call. Both buttons build the script with identical arguments, so the preview always matches the download.

Additional Variables in short

The user picks a mergeable dataset, selects variables in the two-column picker and confirms. store_confirmed_vars() then writes the variables with their merge keys into varlist$data, which the script reads, and into all_lists(), which drives the “Selected Variables” summary. Unticking a variable in the summary excludes it from the script without deleting it (included_vars()). Hovering a variable in the picker shows its question text. The server sends those texts with session$sendCustomMessage("variableQuestiontexts", …), and js_snippets.js attaches them as tooltips.

6 · How a script is assembled

gen_script() contains four complete templates: one for each combination of script type (R, Stata) and format (harmonized spells from the Biography file, or original subspells). Only one runs per call. Every template follows the same idea: the script is a character vector with one element per line, built with c(). Optional parts are written as if (cond) "line". When the condition is false, that expression is NULL, and c() simply drops it.

scripts <- c(
  "# 1. Base: Biography file ----",
  "bio <- read_neps(paste0(datapath, '/', sc, '_Biography_D_', suf_version, '.dta'), english = english)",
  if (work_exp) "# Generate work experience in months",   # NULL when FALSE, dropped by c()
  if (length(datalist) > 0) generate_strings(datalist, english, format = "harmonized")
)
if (education) {                                           # optional chapters are appended afterwards
  chapter <- chapter + 1
  scripts <- c(scripts, gen_qualification_prep_code_r(english, sc, chapter), "")
}

The Additional Variables block is the most intricate part. generate_strings() (R) and generate_strings_stata() loop over the confirmed datasets. For each one they pick a merge strategy from its linkage keys. Datasets merged only by ID_t (like Basics) are joined many-to-one. Spell datasets are joined on ID_t, wave and splink after harmonized episodes are dropped. External-exam datasets are reshaped wide first. The comments inside these functions explain each case.

8 · Worth knowing

  • A closed tab stops the whole app

    app_server() calls shiny::stopApp() when a session ends. That’s handy for local use (closing the browser ends R), but on a server where several users share one R process, one user closing their tab disconnects everyone else on that process.

  • Each tab has its own language switch

    settings_reactive() also returns language, but the settings module has no such input, so it’s always NULL. Explore and Transform each use their own labels switch.

  • Nothing is cached

    Metadata is re-read from the .dta files whenever a dataset or language changes. The files have no rows, so this is usually quick. Loading a dataset into the Additional Variables picker shows a short “Loading variables” modal, because large files like pTarget take a moment.

  • Browser caching is handled

    The CSS and JS links carry ?v= plus the file’s modification time (www_version() in app_ui.R), so browsers pick up style changes after every update.

  • Tooltips are Bootstrap 5, not jQuery

    The bslib theme only loads Bootstrap 5, which has no $.fn.tooltip. window.initAppTooltips() uses bootstrap.Tooltip directly and is re-run after redraws.

9 · Common changes, and where to make them

You want to…Change
Update a cohort to a new SUF releaseReplace the files in inst/extdata/scN_semantic_files/. The version is read from the file names, so no code change is needed. Check that linkage_keys.csv still matches the dataset names.
Make another dataset available in Additional VariablesFill in its Linkage column in linkage_keys.csv, then check that generate_strings() / generate_strings_stata() handle its merge type.
Add a script optionAdd a choice to the sidebar checkboxes in mod_data_transformation.R, pass it into both gen_script() calls (preview and download), and add its lines to all four templates.
Add an exemplary preparation moduleWrite an R and a Stata generator in script_functions.R, add the checkbox, and append it as a chapter in the four templates.
Change stylinginst/www/css/styles.css. The cache-busting link means users see it right after the update.
