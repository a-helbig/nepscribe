How Explore Datasets talks to Transform Data

The logic behind the “Add Selected to Script” feature: one shared object, three fields, and a few rules that keep the two tabs in agreement.

In one paragraph

Shiny modules are sealed off from each other: Explore Datasets can’t read the inputs of Transform Data, and vice versa. So app_server() creates one shared shiny::reactiveValues() object, cross_module, and hands the same object to both modules. Transform Data writes into it what it can accept (its cohort and its mergeable datasets). Explore Datasets reads that to draw the ＋ markers and to filter a selection, then writes an add_request, which Transform Data picks up and merges into the script.

1 · The shared channel

Think of cross_module as a small noticeboard hanging between the two tabs. Each field on it has exactly one writer, so it’s always clear who is responsible for a value. Because it’s a reactiveValues object, anything that reads a field is automatically re-run when that field changes. That’s what makes the other tab react without any explicit “send” call.

Where available_datasets comes from

It’s the exact same list that fills the “1. Step: Select Dataset” dropdown, produced by create_dataset_names() in R/utils.R. That function reads inst/extdata/linkage_keys.csv, keeps rows whose Linkage column is non-empty and whose dataset starts with the selected cohort (e.g. SC6), then appends the SUF version (SC6_Basics_S_17-0-0.dta). Datasets like spChild or spFurtherEdu1 have no linkage entry, because they need extra preparation before they can be merged into a person-year dataset, so they never appear. Because the dropdown and the channel share one source, they can’t drift apart.

3 · Which selected rows get through

When the button is clicked, the Explore server looks at each selected row’s Dataset and Variable and puts it through two checks. Only rows that pass both end up in add_request. Everything else is listed in the alert, with its reason.

4 · Inside Transform Data: one funnel, two stores

Transform Data keeps confirmed variables in two places: varlist$data, which the script generator reads, and all_lists(), which drives the “Selected Variables” summary and the picker. Manual confirmation and requests from Explore go through the same helper, store_confirmed_vars(), so both paths build identical merge information for the script.

5 · Details worth knowing

  • Every session gets its own channel

    app_server() runs once per browser session, and cross_module is created inside it. Two people using the live app at the same time never see each other’s requests.

  • The nonce makes repeated requests fire

    reactiveValues ignore an assignment when the new value is identical to the old one, and then no observer re-runs. add_request therefore carries nonce = runif(1). Without it, sending the same selection twice (e.g. after removing that dataset in Transform Data) would silently do nothing.

  • Row numbers stay correct across pages, sorting and search

    The Explore table uses server-side processing, so input$data_overview_rows_selected returns row indices into the full data_overview_r() table, not positions on the visible page. That’s why selections made on different pages or after a search can be looked up directly.

  • The button behaves like an event, not a value

    “Add Selected to Script” is a DataTables toolbar button whose JavaScript action calls Shiny.setInputValue(…add_to_script, Date.now(), {priority: 'event'}). The changing timestamp and the event priority guarantee that every click reaches the server.

  • The ＋ markers follow Transform Data’s cohort

    output$data_overview reads cross_module$available_datasets. When the cohort changes in Transform Data, the Explore table re-renders with updated markers. Current row selections are cleared as a side effect.

  • The picker mirrors what’s confirmed

    When a dataset is picked, confirmed_selection() pre-selects its confirmed variables, matching on the variable name so it works in both label languages. A separate observeEvent(all_lists()) keeps that selection in sync when variables arrive from Explore or a dataset is removed while it’s open.

  • Why not just return a reactive from a module?

    Returning reactives from a module server is the usual Shiny pattern, but it only works in one direction. Here data flows both ways, and Explore Datasets is created before Transform Data in app_server(). A single shared object avoids a circular dependency and keeps the whole contract visible in one place.
